# Critical Kafka Recovery Candidate - 2026-09-16

## Scope and current status

Target: Hangcha domestic, critical MongoShake only. Baseline:
`ea1175ba8c79f8e945cb7018fa0b3154e669166c` on the dedicated critical release line.
Local candidate branch: `codex-critical-kafka-recovery`.
No production operation, configuration write, restart, replay, container image
build/push or deployment was performed for this recovery patch. The local
validation below preceded PR submission; check the PR for publication/CI status.
The earlier worktree and unrelated `develop` commits were not modified/imported.

The patch fixes two independently verifiable failure modes: an acknowledged
worker remaining alive forever after fencing, and the pinned Sarama producer
hanging on batch retry exhaustion. It does NOT identify the first Kafka error
that triggered the earlier production fence. Missing historical first-cause
evidence must not be replaced by a claim that a local reproduction proves it.

## Upstream evidence

- MongoShake 2.8.4 was published on 2023-04-25:
  <https://github.com/alibaba/MongoShake/releases/tag/release-v2.8.4-20230425>.
- Latest MongoShake release checked on 2026-09-16: 2.8.8, published 2026-04-28:
  <https://github.com/alibaba/MongoShake/releases/tag/release-v2.8.8-20260428>.
  Its `go.mod` still selects Sarama 1.27.2. Replacing the entire collector with
  this release is not a targeted fix and would lose our custom ACK contract.
- Sarama 1.27.2 `retryBatch` returns an error for only the first exhausted
  record, leaving synchronous batch callers waiting for the remaining records.
  The local two-record exhaustion test timed out after 120 seconds before the
  dependency change. Upstream fixed this in PR 2378, merged 2022-12-22:
  <https://github.com/IBM/sarama/pull/2378>.
- The candidate pins Shopify-path Sarama 1.38.1, which includes that fix:
  <https://github.com/IBM/sarama/blob/v1.38.1/async_producer.go>.
  This is a targeted compatibility upgrade, NOT a claim to use the latest
  Sarama release. An IBM module-path migration is outside this incident patch.

## Recovery and safety contract

1. Preserve `acks=all`, idempotence, one in-flight request, fixed partition,
   strict single-source/worker/writer topology and full-worker-batch ACK.
2. Let Sarama retry within the existing producer session (maximum 10 retries).
   Metadata refresh is enabled every 3 minutes, metadata deadline is 10 seconds,
   and dial/read/write deadlines are 10/30/10 seconds. Configured retry backoff
   is 500 ms, but older Sarama idempotent retry paths do not consistently honor
   it; the worker deadline is the wall-clock safety bound, not this backoff.
3. Bound all Kafka chunks of one worker batch by one 120-second delivery
   deadline. On failure/timeout, retain the first cause and fence. Do not replay
   that application batch in the same process, clear the fence, advance ACK,
   skip invalid records, or acknowledge a late completion.
4. A fenced worker or probe exits immediately: 75 for retryable/ambiguous
   failures, 78 for permanent/unknown failures. Do not invoke graceful drain or
   checkpoint flushing on this path. An external supervisor must restart it
   from the existing durable checkpoint. Exit codes alone do not configure a
   supervisor: Kubernetes `Always` restarts both codes, so permanent failures
   remain visible crash loops needing correction rather than silent skipping.
5. Restart is at-least-once, NOT exactly-once. Already accepted prefixes can be
   delivered again across producer sessions. No CFS business deduplication or
   cross-binding replay safety is asserted by this patch.
6. First-cause JSON is exposed in delivery status and written to stderr even
   with file-only application logging: category, retryability, up to 8 safe
   per-record error details, Kafka codes, worker oplog interval/count, time and
   last broker ACK. Keys, values, raw oplog data and credentials are not logged.

New acknowledged-path configuration (process restart required; no live reload):

| Key | Default | Meaning |
| --- | --- | --- |
| `tunnel.kafka.version` | `0.11.0.0` | Explicit wire protocol; must be >= 0.11, preserve compatibility by default |
| `tunnel.kafka.producer.max_message_bytes` | `0` | Retain the existing 18 MiB producer limit; a positive value may lower it |
| `incr_sync.tunnel.kafka.send_timeout_ms` | `120000` | Whole worker-batch Kafka delivery deadline; range 1000-600000 ms |

The broker/topic can enforce a smaller record limit (for example 1 MiB).
Aligning that limit needs an explicitly reviewed runtime configuration; no
record splitting/dropping and no production topic change is part of this patch.
Legacy writer options and ACK semantics are unchanged, but its shared Sarama
dependency changes too; this candidate must not be deployed to the ordinary
lane on the strength of critical-path validation.

## Verification executed locally

Environment: 2026-09-16, macOS arm64, Go 1.26.1, Sarama 1.38.1; Apache Kafka
3.6.2 and Java 11 in an isolated loopback-only fixture on ports 39092/39093.
Kafka records were real; Mongo fetch was not exercised and checkpoint storage
was the existing local HTTP fixture, not production Mongo/CFS/Redis.

- PASS: targeted `TestCritical*` race tests in `tunnel/kafka`, `tunnel`,
  `collector/configure`, `collector/ckpt` and `collector`.
- PASS: temporary replica rejection followed by success; persistent rejection
  returns errors for both records after 11 Produce requests instead of hanging.
- A second dependency A/B check used the same protocol-mock exhaustion test:
  Sarama 1.27.2 still blocked in `syncProducer.SendMessages` at the 10-second
  test deadline; 1.38.1 returned both failures and passed in 0.01 seconds.
  This confirms the code defect, not the first trigger of the production fence.
- PASS: hung sink bounded by deadline; late ACK ignored; no next batch/replay;
  safe first-cause classification and concurrent delivery-status inspection.
- PASS: actual worker subprocess exits 75/78 promptly without checkpoint POST.
- PASS: full `tunnel`, `collector/configure` and `tools/critical-validation`
  suites, including the legacy writer characterization/regression tests.
- PASS: local real-broker tests, run serially with `-p=1`: ordered payloads and
  offsets, 1024-record actual worker delivery with/without batching, 2 MiB
  record isolation, rejected oversized record after accepted prefix, crash
  after broker ACK and restart, and new actual fenced-worker exit/recovery.
  The new test checks exit 78, unchanged durable checkpoint, Kafka code 10 in
  stderr, then fixes only its local test topic and starts a new process. All
  five records arrive; the two accepted prefix records are visibly replayed.
  The child loads the HTTP checkpoint fixture but is explicitly offered the
  same five test records. It does NOT exercise a Mongo reader automatically
  resuming from that checkpoint, nor Kubernetes automatic process restart.
- First combined parallel local-broker invocation had one child producer
  initialization failure before sending. The same test alone and the complete
  serial suite passed. The exact initialization cause was not captured; do not
  describe the initial combined run as green or the fixture as stress-qualified.
- PASS: `go vet -composites=false` on the five targeted packages. Unfiltered
  `go vet` reports existing unkeyed BSON literals in unchanged test/mock files;
  it is NOT a clean unfiltered vet run.
- PASS: `go build -mod=readonly ./...`, native collector build and `CGO_ENABLED=0 GOOS=linux GOARCH=amd64`
  collector build. `go version -m` confirms Sarama 1.38.1, Go 1.26.1 and dirty
  source based on `ea1175ba`; these are local validation binaries, not releases.
- The owned local Kafka fixture was stopped at 14:51 CST; both loopback
  listener ports were checked and no listeners remained.

Reproduction commands from the repository root:

## Release and runtime gates still open

- Review this isolated PR, run CI and build an immutable candidate
  with a pinned, approved toolchain. `go.mod` now declares Go 1.17 due to Sarama;
  local verification used Go 1.26.1, not Go 1.17. Do not reuse the old Go 1.15
  toolchain or assume the repository's historical floating Docker builder is
  suitable. No new container image was built because local Docker was stopped.
- Before authorized deployment, capture current checkpoint and oplog retention
  headroom, validate supervisor restart behavior and the deployed image/runtime
  revision, and preserve the original configuration for rollback. Never reset
  the checkpoint, purge Kafka, enable auto topic changes or disable ACK mode.
- Use isolated replay/business acceptance for bind/unbind/rebind and two
  binding document IDs sharing a logical device key. CFS/Redis convergence and
  duplicate side effects remain unverified, as does Linux container runtime.
- After an approved critical-only rollout, verify fresh oplog/ACK/checkpoint
  deltas, worker/broker errors and CFS consumer/business correlation across a
  bounded recovery observation. A running Pod or green local tests is not
  production recovery acceptance.
